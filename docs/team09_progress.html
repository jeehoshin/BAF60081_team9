서비스 기획

서비스명은 「같이 갈래?」(Activity First)이고, 피칭 자료의 컨셉·흐름·MVP는 확정됐다. 회의에서 추가된 QR 이용자 등록, 조건 매칭, 좋아요 흐름을 피칭의 기본 흐름에 어디까지 합칠지가 남아 있다.

확정 컨셉: 날짜·지역·취향에 맞는 활동을 찾고 함께할 사람과 연결하는 소셜 서비스. 해결하려는 문제는 두 가지다. 공연·축제 정보가 여러 곳에 흩어져 일정 비교가 어렵고, 마음에 드는 활동을 찾아도 같이 갈 사람이 없어 결국 미루게 된다.

확정 사용 흐름 (피칭·목업 기준)

  1. 조건 선택: 날짜(오늘, 이번 주말, 다음 주), 지역(서울 구 단위), 취향(공연, 축제, 전시, 러닝)
  2. 활동 둘러보기: 조건에 맞는 활동 목록과 상세(일시, 장소, 비용, 설명)
  3. 함께할 사람 찾기: 활동별 기존 모임에 참여하거나, 집결 시간·정원을 정해 직접 모임 개설
  4. 데이터 분석: 수집한 활동의 지역별·유형별 분포와 모임 현황

논의 필요

  • 회의 아이디어(조건 매칭, 좋아요 제안 흐름)를 MVP에 넣을지, 발표에서 확장 방향으로만 제시할지
  • QR로 받을 최소 항목: 조건 매칭을 하면 성별·연령대가 필요하고, 안 하면 닉네임만으로도 충분 (실명 대신 닉네임 권장)
  • 인기 분석 기준: 좋아요를 넣지 않으면 모임 참여 수로 대체 가능

서비스 아키텍처

데이터는 두 길로 DB에 들어온다. 이용자 데이터는 화면 → FastAPI → DB로, 행사 데이터는 공공 API → 수집 스크립트 → DB로 적재된다.

피칭 자료와 목업도 같은 구조(공공 API → FastAPI → Supabase → 프론트)이고, 목업은 행사 데이터를 하루 1회 배치로 수집하는 안이다. 소스 코드는 GitHub 저장소 하나에서 관리하고 Vercel과 Render는 이 저장소에서 배포한다. 회의에서 FastAPI 층이 언급되지 않았으니 이 구조로 가는지 팀 확인이 필요하다 논의 필요.

데이터 수집과 출처

공공 API로 행사 정보를 수집한다는 방향은 확정됐고, 어떤 API를 어디까지 적재할지는 호출 테스트 후 정한다. 교수님 요건상 출처(명칭, 제공 기관, URL)를 발표 자료에 반드시 적어야 한다.

러닝 같은 활동은 API가 아니라 이용자가 직접 등록하는 데이터라, 같은 활동 테이블에 출처(API / 사용자)를 구분해 넣는다.

확정

  • 지역은 서울(구 단위) — 피칭·목업의 필터 기준
  • 필요한 정보는 행사명, 유형, 장소, 지역, 일시, 비용 정도. 많이 가져올 필요 없음
  • 수집은 하루 1회 배치 (목업 기준)
  • 호출이 잘 안 되는 API는 빨리 다른 것으로 교체
  • 크롤링은 대체 사이트 서치만 해두고 실제 사용은 지양 (수집이 매우 느림)
  • 인증키는 .env로 분리, 코드에 직접 쓰지 않음

논의 필요

  • 적재 기간: 목업 필터(오늘~다음 주)를 채우려면 최소 2주, 시연 여유를 두면 1~2개월
  • API 3종을 모두 쓸지, 잘 되는 1~2개만 쓸지
  • 유형·지역 값 통일: API마다 분류 체계와 주소 형식이 달라, 공연·축제·전시 4분류와 서울 구 이름으로 맞추는 정제가 필요

참고로 6주차 수업이 공공 Open API(인증키, 페이지 처리, 파싱, 저장) 실습이라, 수업 내용을 그대로 이 수집기에 쓸 수 있다.

DB 테이블 설계

목업은 activities · meetups · participants 3개 테이블로 설계돼 있다. 여기에 회의에서 나온 QR 이용자(users)를 더하고, 좋아요 흐름을 넣는다면 likes까지 두는 안이다. 구현 담당(동주) 검토 전이라 논의 필요.

테이블 근거 주요 컬럼 기본키 외래키 채우는 방식
activities (활동) 목업 유형(공연·축제·전시·러닝), 제목, 장소, 지역(구), 일시, 비용, 설명, 출처(API/사용자) activity_id — 외부 API 배치 수집, 러닝은 사용자 등록
meetups (모임) 목업 대상 활동, 모임 이름, 호스트, 집결 시간, 정원, (연령·성별 조건) meetup_id activity_id, host_id 모임 개설 버튼
participants (참여) 목업 모임, 참여자, 참여 시각, (찬성/반대 응답) (meetup_id, user_id) meetup_id, user_id 참여 버튼
users (이용자) 회의 닉네임, (성별, 연령대, 선호 유형·지역) user_id — QR 입력
likes (좋아요) 회의, 선택 이용자, 활동, 누른 시각 (user_id, activity_id) user_id, activity_id 좋아요 버튼

테이블 관계

  • users ↔ meetups: 다대다 → participants로 연결
  • users ↔ activities: 다대다 → likes로 연결 (likes를 넣을 경우)
  • meetups → activities: 모임 하나는 활동 하나에 속함
  • 괄호 안 컬럼은 조건 매칭·좋아요 흐름을 MVP에 넣을 때만 필요

설계 포인트

  • 참여자를 모임 테이블 컬럼(참여자1, 참여자2…)으로 늘리지 않고 연결 테이블로 분리 → 인원 집계, "내가 참여한 모임" 조회가 단순해짐
  • 연결 테이블 덕분에 JOIN 쿼리를 시연할 수 있어 DB 연동 평가에 유리
  • 이 표가 그대로 발표용 "DB 테이블 문서"의 뼈대가 됨

백엔드 API

논의 필요 교수님 안내와 피칭 자료 모두 백엔드를 FastAPI(Render)로 두고, Swagger UI 주소와 API 설명 문서를 발표 자료에 넣도록 하고 있다. 회의에서는 프론트가 Supabase에 바로 붙는 식으로 이야기됐으니, 피칭 구조대로 가는 것으로 팀 확인이 필요하다.

  • FastAPI로 만들면 Swagger UI(/docs)가 자동 생성돼 주소 요건이 함께 해결됨
  • 매칭·통계 쿼리를 백엔드에 두면 "버튼 하나하나가 DB와 연결돼 있다"는 시연 포인트가 더 분명해짐
  • 3~4주차 실습(가계부 API를 FastAPI + Supabase로 배포)과 같은 구조라 실습 코드를 참고할 수 있음

데이터 분석·정리 페이지

확정 피칭 MVP에 수집 행사의 지역별·유형별 분포 분석이 이미 들어 있어, 교수님 필수 페이지 요건(수집 데이터 설명과 기초 분석)과 맞는다. 여기에 목업의 모임 현황 지표와 회의에서 합의한 이용자 통계·인기 분석을 더한다.

구분 분석 예시 쓰는 테이블 근거
A. 수집 데이터 설명 출처별 수집 건수, 수집 기간, 컬럼 설명 activities 교수님 요건
A. 수집 데이터 분석 지역별·유형별 활동 분포 activities 피칭 MVP
B. 모임 현황 열린 모임 수, 참여 인원, 평균 충원율, 유형별 참여 인원 meetups + participants 목업
B. 이용자 통계 연령대·성별·선호 유형 분포 users 회의
B. 인기 분석 참여(또는 좋아요) 많은 활동·유형 순위 participants 또는 likes + activities 회의
B. 교차 분석 연령대별 선호 유형 users + participants + activities 회의, JOIN 시연에 적합

시연 방식 확정

  • 당일 QR 입력만으로는 표본이 수십 명이라 통계가 빈약 → 더미 이용자·좋아요 데이터를 미리 적재
  • 발표 중 QR 데이터가 더해지면서 분포·순위가 바뀌는 모습을 보여줌
  • 더미 데이터 생성은 Gemini 등 AI 활용 (실제 수강생 정보는 AI에 넣지 않음)

비즈니스 모델

논의 필요 발표 필수 항목이지만 회의에서는 필요하다는 점만 확인했다. 교수님 요건은 세 가지를 답하도록 한다.

요건 답해야 할 질문 현재
대상 고객 누가 쓰는가 피칭: 취미·여가를 함께할 사람을 찾는 누구나. 발표용으로는 더 좁히는 게 설득력 있음
제공 가치 이용자와 행사 주최 측이 각각 얻는 것 피칭의 문제 정의(흩어진 정보, 같이 갈 사람 부재)에서 도출 가능
수익 또는 지속 운영 어떻게 돈을 벌거나 유지하는가 미정

검토해볼 만한 방향 (회의에서 논의되지 않은 예시): 행사 주최 측 유료 노출·홍보 제휴, 공연 예매처 제휴 수수료, 지자체 축제 홍보 협력. 서비스 운영 데이터(인기 행사, 연령대별 선호)를 주최 측에 제공하는 모델은 분석 페이지와도 이어진다.

평가 요건 대비 현황

피칭 자료와 목업까지 반영하면 요건 미충족은 없다. 마지막 남았던 출처 명시 1개도 인증키 발급으로 정보를 확보했다. 대신 피칭과 회의 내용이 어긋나는 세 곳을 팀에서 맞춰야 한다: 백엔드 구조(피칭은 FastAPI, 회의는 Supabase 직접 연결), 매칭 방식(목업은 단순 참여·개설, 회의는 조건 매칭·좋아요), 프론트(목업은 React, 회의는 HTML).

역할 분담과 담당자별 할 일

5개 역할은 확정됐다. 다만 FastAPI 백엔드를 Render에 누가 올릴지는 정해지지 않았고, 아래는 동주(구현)·지호(배포)로 나누는 안이다.

화면(HTML)은 지호, 백엔드(FastAPI)·매칭 쿼리·QR은 동주가 만든다. 둘은 '백엔드 API' 섹션의 엔드포인트 목록으로 연결된다. HTML의 버튼이 그 목록의 주소를 호출하면 FastAPI가 DB를 조회·저장하고 결과를 돌려주는 구조라, 이 목록을 두 사람이 먼저 확정해야 병렬 작업이 가능하다.
