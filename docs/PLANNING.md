## 0. 서비스 개요

공공 데이터로 서울·대전의 공연·축제·전시를 모아 **어디서 무엇이 열리는지** 보여 주고, 혼자 가기 망설여지는 사람끼리 **모임을 열고, 참여하고, 모임톡으로 만나는** 서비스입니다. 러닝처럼 공공 데이터에 없는 활동은 이용자가 직접 올립니다.

| 구분 | 내용 |
|---|---|
| 문제 | 공연·축제·전시 정보가 예매처·지자체·기관 사이트로 흩어져 있고, 같이 갈 사람이 없어서 포기한다 |
| 해결 | ① 공공 API 3개를 모아 정제해서 날짜·지역·유형으로 탐색 ② 지역별 공급 현황을 분석해 보여 줌 ③ 활동마다 모임을 열고 모임톡으로 연결 |
| 대상 | 20~40대 |
| 지역 | 서울 25개 구 + 대전 5개 구 (`'OO구'` 형식) |
| 데이터 | KOPIS 공연예술통합전산망, 한국관광공사 TourAPI, 한국문화정보원 한눈에보는문화정보, 구별 주민등록 인구 |

**발표 스토리 한 줄**

> 공공 데이터로 공연·축제·전시의 **지역 격차**를 발견했다 → 그래서 정보를 한곳에 모으고, **동행 모임**으로 참여 장벽을 낮추는 서비스를 만들었다 → 오늘 이 자리에서 여러분이 QR로 직접 참여해 본다.

## 1. 기획 방향: 데이터 활용 중심

### 1-1. 고민

기획을 다듬는 동안 모임 기능 아이디어가 계속 늘었습니다. 직접 개설 모임 종류 확대, 예비 인원, 모임장 양도, 추천 목록 등입니다. 그러다 이런 질문이 생겼습니다.

> 이 과제는 외부 API로 데이터를 모아 활용하는 데 중점이 있는데, 모임을 만들고 취소하고 양도하는 기능에 힘을 줄 필요가 있을까? 데이터 활용에 더 무게를 실어야 하지 않을까?

### 1-2. 판단 근거

| 근거 | 내용 |
|---|---|
| 평가의 중심 | 과제 요건은 외부 API·공공 데이터 수집, DB 구조화, 데이터 분석 페이지, API·DB 문서. 프론트엔드는 평가에서 빠짐 |
| 모임 기능의 성격 | 만들기·취소·양도·예비 인원은 어느 서비스에나 있는 게시판형 기능이라, 정교하게 만들어도 "데이터를 잘 활용했다"는 평가로 이어지지 않음 |
| 이미 된 것 | 저장소에 모임 개설·참여·정원 확인·조건 확인·모임톡·지도·라이브 보드가 이미 있음 (2장). 시연에 필요한 모임 기능은 충분 |
| 비어 있는 것 | 공공 API는 KOPIS·TourAPI 목록 수집만 연결됨. 한눈에보는문화정보, KOPIS 통계, 출처 간 중복 처리, 수집 기록, 분석 지표가 비어 있음 |
| 개발 인력 | 개발자가 한 명. 남은 열흘을 평가받는 쪽에 써야 함 |

### 1-3. 결정

**데이터 7, 모임 3으로 노력을 배분합니다.** 모임은 지금 있는 기능에 규칙 몇 가지만 다듬고, 새 모임 기능은 "향후 계획"으로 발표에서 소개합니다.

| 구분 | 이번에 하는 것 | 향후 계획 (발표에서 소개) |
|---|---|---|
| 데이터 | 한눈에보는문화정보 연결, KOPIS 통계 수집, 출처 간 중복 처리, 수집 기록, 인구 대비 공급 지수, 분석 화면 지표, KOPIS 안내 문구 | 매일 자동 수집, 서울·대전 밖 지역 확대 |
| 모임 | 정원 4~20명, 조건 미충족 모임 회색 표시, 참여자 "30대(여)" 표시, 등록 화면 값 정리 | 예비 인원, 모임장 양도·모임 취소, 사용자 활동 유형 확대(등산·맛집 탐방·보드게임·풋살), 개인화 추천 |

### 3-3. 한눈에보는문화정보 연결 `[개발]` 영선

### 3-4. KOPIS 통계 수집 `[개발]` 영선

분석 페이지의 지역 격차 근거입니다. 목록 수집과 달리 **전국 단위 집계**라서, 서비스 지역이 서울·대전뿐이어도 "공연 시장이 어디에 몰려 있나"를 보여 줄 수 있습니다.

| 통계 | KOPIS API | 저장할 값 | 쓰는 지표 |
|---|---|---|---|
| 지역별 | `prfstsArea` | 시·도별 공연 건수, 상연 횟수, 티켓 판매 수, 매출액 | 4-1 A |
| 장르별 | `prfstsCate` | 장르별 같은 값 | 4-1 B |
| 일자별 | `prfstsTotal` | 날짜별 같은 값 (요일은 계산) | 4-1 C |

- 조회 기간은 1회 최대 31일이라, 최근 3개월을 한 달씩 나눠 받습니다.
- 새 테이블 하나(`kopis_stats`: 종류, 기간, 기준값, 지표들, 수집일)에 저장합니다. `activities`와는 연결하지 않습니다.
- 수집기의 KOPIS 호출 간격 규칙(1초에 4건)을 그대로 씁니다.

### 3-5. 출처 간 중복 정리 `[개발]` 영선·동주

| 분류 | 겹칠 수 있는 출처 | 남기는 쪽 |
|---|---|---|
| 공연 | KOPIS, 한국문화정보원, 한국관광공사(EV02) | KOPIS (상세·시설·통계가 가장 풍부) |
| 축제 | 한국관광공사, 한국문화정보원 | 한국관광공사 |
| 전시 | 한국문화정보원, 한국관광공사 | 한국문화정보원 |

- 같은 행사 판단: 제목(띄어쓰기·괄호 제거) + 시작일 + 'OO구'가 같음
- 방법: `activities`에 `dedup_key` 칸을 두고, 목록 API에서 같은 키는 우선순위가 높은 것 하나만 보여 줌. 원본은 지우지 않음 (모임이 걸려 있을 수 있고, 규칙을 바꿔도 다시 수집할 필요가 없음)
- 분석의 "출처별 건수"는 중복 정리 전 기준, "활동 수"는 정리 후 기준으로 씁니다.

### 3-6. 수집 기록 `[개발]` 동주

`POST /collect`가 이미 돌려주는 숫자(`collected`, `inserted`, `updated`, `unchanged`, `skipped`, `error`)를 출처·지역별로 새 테이블 `collect_runs`에 저장합니다. 데이터 품질 지표(4-1 H)의 재료가 됩니다.

### 3-7. 데이터 기반 탐색 화면 `[개발]` 지호

| 기능 | 내용 | 데이터 처리 |
|---|---|---|
| 날짜 필터 | 오늘 / 이번 주말 / 다음 주 (한국 시간, v0.1 정의 그대로) | API의 기간 겹침 필터 (있음) |
| 정렬 | 진행 중이거나 곧 시작하는 것 먼저, 끝난 것은 맨 뒤 | 있음 |
| 곧 끝나는 것 | 2주 안에 끝나는 공연·전시 표시 | `ends_at` 기준 |
| 출처 표시 | 활동 카드·상세에 출처 배지 (KOPIS / 한국관광공사 / 한국문화정보원 / 사용자) | `source` |

발표 날 날짜 필터가 비지 않도록, 발표 전날(10/20) 수집을 한 번 더 돌리고 범위에 11/1까지 들어가게 합니다.

## 4. 분석 페이지

**원칙:** 공공 데이터 지표가 중심이고, 이용자 지표는 **발표 당일 청중이 QR로 만든 실제 데이터**로 보여 줍니다. 미리 넣은 시연용 데이터와 섞이지 않도록 "전체 / 오늘 QR 참여자만"을 바꿔 볼 수 있게 합니다. 더미 여부 칸 없이 `users.created_at`이 발표 시작 이후인지로 나눕니다.

### 4-1. 지표 목록

| 번호 | 지표 | 알고 싶은 것 | 데이터 | 차트 | 상태 |
|---|---|---|---|---|---|
| A | 시·도별 공연 매출액·티켓 판매 비중 | 공연 시장이 서울에 얼마나 몰려 있나 | KOPIS 통계 지역별 | 가로 막대 (상위 10 + 기타) | `[개발]` |
| B | 장르별 공연 건수와 매출액 | 많이 열리는 장르와 돈이 되는 장르가 같은가 | KOPIS 통계 장르별 | 막대 2개 나란히 | `[개발]` |
| C | 요일별 평균 상연 횟수·티켓 판매 | 공연은 언제 몰리나 → 모임은 언제 열려야 하나 | KOPIS 통계 일자별 | 세로 막대 (월~일) | `[개발]` |
| D | 구별 활동 수 (공연·축제·전시·러닝) | 어느 구에 무엇이 많은가 | `activities` | 누적 가로 막대 | 있음 (유형 구분 추가) |
| G | 인구 10만 명당 활동 수 (구별, 서울 vs 대전) | 인구를 감안해도 격차가 있나 | `activities` + 인구 | 가로 막대 + 평균선 | `[개발]` |
| E | 출처별 활동 수 | 세 출처가 각각 무엇을 채우나 | `activities.source` | 도넛 또는 막대 | 있음 |
| H | 데이터 품질 | 데이터를 믿을 수 있나 | `collect_runs` + `activities` | 숫자 카드 + 표 | `[개발]` |
| U | 이용자 연령대·성별·선호 유형 | 오늘 참여한 청중은 누구인가 | `users` (오늘 QR 참여자만 보기) | 막대 | 있음 (보기 전환 추가) |
| M | 모임 수·참여 인원·채움률 | 오늘 모임이 얼마나 만들어지고 찼나 | `meetups`, `participants` | 숫자 카드 | 있음 (보기 전환 추가) |

H에 넣을 것: 최근 수집 시각과 결과, 출처별 수집·저장·제외 건수, 제외 이유별 건수(기간 밖, 장기 행사, 구 불명), 출처 간 중복 정리 건수, 이미지·좌표가 빈 비율.

### 4-2. 분석 결과 섹션의 가설

가설과 다르게 나와도 그 자체가 분석 결과이니 그대로 씁니다.

| 가설 | 지표 | 결과 | 서비스에 주는 의미 |
|---|---|---|---|
| 공연 매출은 서울에 집중되어 있다 | A | 서울 비중 `[데이터로 채움]`% | 서울 밖에서는 정보를 찾기 더 어렵다 → 한곳에 모으는 서비스의 근거 |
| 인구를 감안해도 서울과 대전의 공급 차이가 크다 | G | 인구 10만 명당 서울 `[ ]`건 / 대전 `[ ]`건 | 대전처럼 공급이 적은 지역일수록 축제·사용자 활동(러닝)의 비중이 커진다 |

### 4-3. 반드시 넣을 안내·출처 문구 `[개발]` 지호

KOPIS 자료가 나오는 곳(활동 상세의 KOPIS 공연, 분석 A·B·C 아래)에는 다음 문구를 넣습니다. 찬휘가 KOPIS 이용 안내에서 확인한 내용입니다.

> 집계기간: 최종집계 YYYY.MM.DD / 집계대상: 모든 공연 데이터 전송기관 / 집계 데이터는 공연예술통합전산망 연계기관의 티켓판매시스템에서 발권된 분량 기준이므로 해당 공연의 전체 관객 수와 차이가 있을 수 있습니다.

"최종집계" 날짜에는 KOPIS 통계를 수집한 날짜를 넣습니다. 한국관광공사 이미지는 공공누리 유형을 따르고(자르거나 고치지 않음), 한국문화정보원 자료와 인구 지표에도 출처와 기준 시점을 적습니다.

## 8. 발표 시연 흐름

발표는 슬라이드 없이 **팀 프로젝트 페이지**로 진행하고, 최대 15분·목표 10분입니다. QR 시연은 v0.1의 흐름을 유지하고, 그 앞에 데이터 설명을 둡니다.

| 시간 | 내용 | 화면 |
|---|---|---|
| 데이터 파트 | 세 출처 → 정제 → 중복 정리 → 저장 흐름 설명, 데이터 품질 숫자 | 프로젝트 페이지 아키텍처 섹션, 분석 H |

| 0:00 | QR 띄우고 "닉네임과 간단한 정보만 골라 주세요" | `qr.html` |
| 0:20 | 등록되는 동안 라이브 보드로 숫자가 늘어나는 장면 | `live.html` |

| 1:50 | 분석 화면을 "오늘 QR 참여자만"으로 바꿔 청중 분포와 모임 채움률 보여 주기 | `stats.html` |

**미리 준비할 것:** 발표 전날 수집 다시 실행, 서울 마포구·대전 유성구에 조건이 다른 시연 모임 여러 개, 일반 창·시크릿 창에 서로 다른 이용자(30대 여성, 20대 남성) 등록, 발표 직전 Render 서버 깨우기, 실패 대비 녹화본, 발표 후 QR 이용자 데이터 삭제.

공연·축제·전시는 공공 API에서 받은 것만 씁니다. 시연용으로 행사를 지어내지 않습니다 (`CLAUDE.md` 규칙).
